# Test Coverage and Quality Analysis (`dotnet-coverage-analysis`)

## Overview
Provides end-to-end workflows for collecting, visualizing, and analyzing code coverage and test quality in the **Job Tracker Backend** using **Coverlet (`coverlet.collector`)**, **`Microsoft.NET.Test.Sdk`**, and **ReportGenerator**.

## Activation Instructions
Activate this skill whenever you are:
- Running tests with code coverage collection (`XPlat Code Coverage`).
- Generating human-readable HTML, Cobertura, or Markdown coverage reports with `ReportGenerator`.
- Analyzing line coverage, branch coverage, method coverage, and cyclomatic complexity to locate untested business logic or missing edge cases.
- Configuring `.runsettings`, `[ExcludeFromCodeCoverage]`, or coverage thresholds.

## Specific Responsibilities
1. **Collect Accurate Cross-Platform Coverage**: Use `dotnet test --collect:"XPlat Code Coverage"` with a `.runsettings` file that excludes generated EF Core migrations and boilerplate program bootstrap files.
2. **Prioritize Branch Coverage & Critical Paths Over Vanity Metrics**: Focus testing efforts on domain invariants, state transitions, validation logic, and error branches (`if/else`, `switch`, null-coalescing branches) rather than chasing 100% line coverage on trivial properties.
3. **Uphold Strict Quality Guardrails**:
   - **Never** write assertion-free or meaningless tests solely to inflate coverage numbers.
   - **Never** modify or delete valid production code solely to improve coverage metrics.

## Technology-Specific Implementation Guidance

### 1. Understanding Coverage Metrics
- **Line Coverage**: Percentage of executable lines executed during the test run. Useful as a baseline, but can hide untested conditional expressions on a single line.
- **Branch Coverage**: Percentage of decision branches (`if`, `else`, `switch` arms, `?:`, `??`) evaluated in both `true` and `false` directions. **The most important metric for business logic reliability.**
- **Method Coverage**: Percentage of methods invoked at least once.

### 2. Configuring `coverlet.runsettings`
Exclude auto-generated EF Core migrations and DTO records that contain no business logic so coverage metrics reflect real application behavior:
```xml
<?xml version="1.0" encoding="utf-8" ?>
<RunSettings>
  <DataCollectionRunSettings>
    <DataCollectors>
      <DataCollector friendlyName="XPlat code coverage">
        <Configuration>
          <Format>cobertura,opencover</Format>
          <Exclude>[*.Tests*]*,[*]*.Migrations.*,[*]Program</Exclude>
          <ExcludeByAttribute>Obsolete,GeneratedCodeAttribute,CompilerGeneratedAttribute,ExcludeFromCodeCoverageAttribute</ExcludeByAttribute>
          <SingleHit>false</SingleHit>
          <UseSourceLink>true</UseSourceLink>
          <IncludeTestAssembly>false</IncludeTestAssembly>
        </Configuration>
      </DataCollector>
    </DataCollectors>
  </DataCollectionRunSettings>
</RunSettings>
```

### 3. Selective Code Exclusion (`[ExcludeFromCodeCoverage]`)
Apply `[ExcludeFromCodeCoverage]` only to infrastructure bootstrap code or auto-generated code—never to business services or domain logic:
```csharp
using System.Diagnostics.CodeAnalysis;

[ExcludeFromCodeCoverage(Justification = "EF Core design-time factory used only by CLI tooling.")]
public sealed class DesignTimeDbContextFactory : IDesignTimeDbContextFactory<JobTrackerDbContext>
{
    // ...
}
```

### 4. Analyzing Coverage Reports to Find Missing Tests
When inspecting `coverage.cobertura.xml` or `Summary.md` generated by ReportGenerator:
1. **Locate Classes with Low Branch Coverage (< 80%)**: Inspect partially covered conditions (`condition-coverage="50% (1/2)"`).
2. **Identify Critical Risk Hotspots**: Methods with high Cyclomatic Complexity and low Branch Coverage are the highest-priority candidates for new parameterized `[Theory]` unit tests.
3. **Design Meaningful Tests**: For each uncovered branch, determine the business scenario that triggers it (e.g., invalid status transition, null optional salary, unauthorized user) and write a behavior-verifying test.

See [Coverlet and ReportGenerator Reference](./references/coverlet-and-reportgenerator.md) for CI threshold enforcement and Cobertura XML analysis commands.

## CLI Commands
```powershell
# 1. Run all tests
dotnet test

# 2. Collect cross-platform code coverage (generates coverage.cobertura.xml in TestResults/<guid>/)
dotnet test --collect:"XPlat Code Coverage" --results-directory ./TestResults

# 3. Collect coverage using a custom .runsettings configuration
dotnet test --collect:"XPlat Code Coverage" --settings coverlet.runsettings --results-directory ./TestResults

# 4. Generate HTML and Markdown summary reports using ReportGenerator
reportgenerator `
  -reports:"./TestResults/**/coverage.cobertura.xml" `
  -targetdir:"./TestResults/CoverageReport" `
  -reporttypes:"HtmlInline;TextSummary;MarkdownSummaryGithub"

# 5. View the text summary directly in the terminal
Get-Content ./TestResults/CoverageReport/Summary.txt
```

## Common Mistakes to Avoid
1. **Assertion-Free Tests ("Coverage Gaming")**: Calling methods without asserting their outputs or side effects just to turn red lines green.
2. **Accumulating Stale `TestResults` Folders**: Running `reportgenerator` with a wildcard `-reports:"./TestResults/**/coverage.cobertura.xml"` without cleaning old runs merges outdated coverage files. Clean `./TestResults` before collecting fresh coverage.
3. **Ignoring Branch Coverage**: Celebrating 90% line coverage when complex `switch` or ternary expressions only have 50% branch coverage.
4. **Altering Production Code for Coverage**: Removing defensive null checks or error handling in production code just because they were hard to trigger in a unit test.

---

## Verification Checklist
- [ ] `./TestResults` directory is cleaned before running a new coverage collection pass.
- [ ] `dotnet test --collect:"XPlat Code Coverage"` completes with all tests passing.
- [ ] Auto-generated migrations and test assemblies are excluded from coverage calculations.
- [ ] Both **Line Coverage** and **Branch Coverage** are reviewed in the ReportGenerator summary.
- [ ] Every newly added test asserts meaningful business behavior, edge cases, or error contracts.
